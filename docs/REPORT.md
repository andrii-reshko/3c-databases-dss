## Мета роботи

Моєю метою було створити програму DSS, яка допоможе зберігати і впорядковувати дані для вибору найкращих лідів на онлайн-біржі типу Upwork. Я мав на увазі альтернативи, тобто самі замовлення, критерії для їх оцінки, і, власне, самі оцінки. Також, я одразу заклав таку архітектуру, щоб у майбутньому можна було без проблем додати аналітичний блок, який би сам все рахував.

## Завдання

Переді мною стояло кілька завдань: 
1. розробити систему для роботи з альтернативами, критеріями та їх оцінками. Це включало реалізацію функціоналу для їх додавання, редагування та перегляду. 
2. Мав забезпечити можливість вводити оцінки для кожної альтернативи за кожним критерієм і потім бачити все це у вигляді матриці. 
3. Для зберігання даних я вирішив використати реляційну базу даних, а саме SQLite, бо вона проста і не потребує окремого сервера. 
4. Спроектувати архітектуру так, щоб у майбутньому можна було легко підключити аналітичний компонент. 
5. Підготувати даний звіт.

## Домен
DSS для швидкого вибору оптимального замовлення на платформі Upwork для IT-агенції.

Предметна область охоплює сферу IT-аутсорсингу, фрілансу та специфіку роботи агенцій на платформі Upwork.

Це висококонкурентне середовище де успішність біддінгу (подачі заявок на проєкти) залежить від швидкості реакції, правильного розподілу ресурсів та аналізу клієнта.

### Постановка задачі
Завдання полягає у формулюванні задачі прийняття рішення щодо вибору найкращого замовлення для подачі пропозиції (proposal). Користувачем системи є Lead Generation Specialist (лідген) або менеджер з продажу. Система повинна допомогти визначити найкращий проєкт серед доступних, щоб максимізувати шанси на отримання контракту та мінімізувати марні витрати Конектів (внутрішня валюта платформи)

### Джерела даних
Вхідні дані збираються зі сторінок пошуку роботи (Job Feed) та публічних профілів клієнтів на платформі Upwork.

Дані можуть вноситися лідгеном у DSS вручну або автоматично збиратися за допомогою API.

Якщо дані клієнта видимі то можливе отримання додаткової інформації через спеціалізовані соцмережі типу LinkedIn.

### Обмеження
Система в ідеалі має врахувати наступні обмеження при яких альтернатива відхиляється без подальшого оцінювання:

Час публікації роботи перевищує 24 години (оскільки дуже висока конкуренція навіть на великі і складні ентерпрайз проєкти)

Клієнт не має підтвердженого методу оплати (з великою долею ймовірності він просто зондує почву але без серйозних намірів)

Відсоток найму (Hire Rate) клієнта становить менше 20%. Але за винятком абсолютно нових клієнтів на платформі (оскільки їх рано списувати з рахунку).

Вартість подачі заявки перевищує адекватну границю конектів для агенції.

### Очікуваний результат для бізнесу
Кінцевим результатом роботи самої системи буде ранжований список проєктів від найменш привабливих до найбільш привабливих.

Це дозволить:
- Шортлістити список робіт – при використанні UI платформи це нетривіальна задача оскільки у висококонкурентній ніші треба перебрати близько сотні постів за годину.
- Швидше подавати комерційні пропозиції, що дуже важливо при високій конкуренції.
- Відповідно зменшити операційні витрати на стафф агенції і збільшити дохід.

## Хід роботи

Роботу я почав з аналізу предметної області — вибору лідів на Upwork. Треба було зрозуміти, які дані важливі для прийняття рішень. 

Далі я спроектував архітектуру застосунку. Це веб-застосунок. Я вирішив використати гексагональну архітектуру: обробники HTTP-запитів, репозиторії для роботи з даними та доменні сутності. 

Для бази даних я обрав SQLite. Створив три основні таблиці: `alternatives`, `criteria` та `evaluations` для зв'язку між ними. 

Після проектування я перейшов до коду на Go. Написав моделі для сутностей `Alternative`, `Criterion` та `Evaluation`. 

Потім реалізував репозиторії для кожної з них, які виконують стандартні CRUD-операції. 

Для веб-інтерфейсу я використав фреймворк Gin. Створив обробники запитів, які реагують на дії користувача, типу додавання нового критерію чи редагування альтернативи. 

Далі реалізував матрицю оцінювання. Це, в принципі, головний екран системи, де можна бачити всі альтернативи, всі критерії і вводити для них оцінки. 

Зберігання цих оцінок я реалізував через операцію `UpsertBatch`, щоб ефективно оновлювати дані в базі. Також, як і вимагалось у завданні, я передбачив місце для майбутнього аналітичного модуля. 

Я створив інтерфейс `AnalyticsService` з методом `RankAlternatives`. Поки що це просто заглушка, але вона показує, куди можна буде вбудувати логіку ранжування. 

Наприкінці я заповнив базу тестовими даними, щоб продемонструвати роботу системи. Я додав три альтернативи-замовлення та кілька критеріїв для їх оцінки.
